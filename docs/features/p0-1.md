# P0.1 Snapshot archive

Linear: MED-72. Flag: `snapshot_archive`, off by default (also in production). Entitlement: none yet (see below).
Design note: the revision-2 design comment on MED-72.

## What it does

Until now OddVex stored no market data: the board read the provider's current quotes on every request. The snapshot
archive keeps an append-only record of what the provider reported, so the app can answer "what did OddVex know at
time T?":

- every book's quote for every game market (moneyline, spread, total), with its status and `last_updated`;
- every book's player-prop offer;
- the event state that staleness depends on (status, start time, score, `score_updated_at`);
- the stale thresholds in force at each capture, which decide which quotes count toward best price and consensus;
- lineup, injury, news and weather status records, once a source exists (P0.5). Only a status, a source name and
  times are stored, never article or headline text.

Two reads are built on it:

1. **As of T.** `ArchiveView` (`services/api/src/oddvex_api/archive/view.py`) is a read-only data provider that
   answers only from rows captured at or before T. It is handed to the existing `Board`, so the best price and the
   no-vig consensus as of T come from the same, already tested code as the live board (`board.py`, `quant/`). Its
   staleness is judged at T with the thresholds stored on the capture run. One difference from the live board: a game
   archived as `upcoming` whose start time had passed at T is judged by the live threshold (120 s), so a pregame
   quote never passes as an in-play price; the game keeps the status it was captured with in every response.
2. **Placement-time prices.** For every leg of a stored bet, `placement_prices`
   (`archive/placement.py`) returns either `priced`, with the best price overall and the best price at the user's
   books as of the bet's `placed_at`, or `cannot_price` with a named reason.

No new calculation was added. The changes to `Board` are additive and leave the live board unchanged:
`best_price(..., books=...)` keeps only the user's sportsbooks; `quote_rows` is a public name for the rows `best_price`
and `event_odds` judge; `freshness_status(event)` names the status whose stale threshold applies (the event's own
status on the live board).

## How to switch it on

1. Turn the flag on: `PUT /v1/admin/flags/snapshot_archive` with `{"enabled": true}` (administrators only).
2. Capture: on the preview the worker container runs `python scripts/capture_snapshots.py` every 120 s
   (`infrastructure/hostinger/compose.yaml`). Locally there is no worker; run it by hand from `services/api`:

   ```bash
   .venv/bin/python scripts/capture_snapshots.py               # capture what is due, prune when due
   .venv/bin/python scripts/capture_snapshots.py --force       # capture now, whatever the intervals
   .venv/bin/python scripts/capture_snapshots.py --prune-only  # prune when due (with --force: now)
   .venv/bin/python scripts/capture_snapshots.py --dry-run     # what a pass would capture; writes nothing
   .venv/bin/python scripts/capture_snapshots.py --stats       # size, row counts, latest runs
   ```

While the flag is off the script prints "Snapshot archive is off; nothing captured." and writes nothing, so turning
the flag off stops all growth. It also stops the prune: the rows already stored stay, past the 7- and 400-day
retention, until the flag is on again and the next prune removes them. The only other way to remove them is migration
0008's downgrade, which drops the five archive tables. The Founder and counsel should know this for OQ-23 (e).

Before switching it on in the preview, read owner question OQ-23.

## API

All routes are additive. The user routes need sign-in and answer `404 feature_disabled` while the flag is off.

| Route | What |
|---|---|
| `GET /v1/archive/events/{event_id}/odds?market=&as_of=` | The event's coverage at `as_of` and, only when it is `captured`, each book's stored quote from the covering capture and the odds comparison (`EventOddsOut`) as of `as_of` |
| `GET /v1/archive/players/{player_id}/props?as_of=&market=` | The props coverage at `as_of` and, when it is `captured`, the latest offer per game, market and book at or before `as_of`, for each of the player's games with an offer in the 48 hours before `as_of`; a game whose offers were all withdrawn or that had left scope (tombstones) is left out, and so is a game the prune has reduced to closing offers that are no longer the answer at `as_of` (listed in `pruned_event_ids`) |
| `GET /v1/archive/events/{event_id}/status?as_of=` | The latest status record per team or player and kind at or before `as_of` (empty until P0.5) |
| `GET /v1/bets/{bet_id}/placement-prices?books=` | Placement-time prices for each leg of your own bet; another user's bet answers 404 like a missing one |
| `GET /v1/admin/archive/stats` | Administrators only, not behind the flag: size, row counts, latest run of each kind. Audited as `admin.read` |

`as_of` must carry a time zone offset (422 `as_of_without_offset`) and may be at most 60 s past the provider's clock
(422 `as_of_in_future`).

**Coverage of an event at T** is read from R, the latest successful odds capture at or before T (capture runs are
kept 400 days):

- `captured`: R is at most 840 s before T (`ODDVEX_SNAPSHOT_MAX_GAP_SECONDS`: two odds intervals plus one worker
  turn, so one missed pass is tolerated and two are not) and the archive holds the event's row from R. Only then is
  anything priced, and always from R: an older kept capture never stands in for a pruned one;
- `archive_gap`: no successful odds capture within 840 s before T;
- `archive_pruned`: R ran while the game was in scope (between 36 hours before its start and its last capture), but
  the game's rows from R were pruned; or no run is left from before T and T is past the 400-day horizon;
- `not_captured`: before the first capture, or the game was not in scope at R (for example three days before it,
  or after it ended).

Quotes and the comparison are returned only when the status is `captured`: an older kept capture is not the market
at T.

**Coverage of a player's props at T** is read from P, the latest successful props capture at or before T:
`captured` when P is at most 7,320 s before T (two props intervals plus one 120 s worker turn), `archive_gap` when it
is older, `not_captured` before the first props capture, and `archive_pruned` when no run is left from before T and
T is past the 400-day horizon. Offers are returned only when `captured`. After the prune a game keeps only its
closing offers (per offer, the latest row at or before its closing capture). Those are served for T only while they
are still the answer: from each kept offer's capture until the first props capture after the closing capture.
Otherwise the game's offers are left out and its id is listed in `pruned_event_ids`, for any T from its first props
capture to 48 hours after the props capture that tombstoned its offers. Candidate games are those with a prop row of
the player, or an event row of the player's current team, within a few days of T.

**A leg's answer** is `priced` (best price at your books found) or `cannot_price` with `reason`:

- `leg_not_structured`: the leg has no event, no outcome, a market other than moneyline, spread or total, or no line
  for a spread or total (for example a typed player prop);
- a coverage status: `not_captured`, `archive_gap`, `archive_pruned`;
- `stale_at_placement`: open, fully priced quotes for the outcome existed, but every one was stale at `placed_at`
  (including a pregame quote for a bet placed after the start time, judged by the 120 s live limit);
- `no_usable_quote`: no open quote for the outcome on the leg's line;
- `none_at_your_books` or `books_unknown`: a price existed, but not at your books, or no books are known for you.
  `best_overall` then holds that price, and `your_books_reason` carries the same value.

`reason` is null only when the leg is `priced`. The best price uses the latest capture at or before `placed_at`,
judges staleness at `placed_at`, excludes stale, suspended and unavailable books, and for spread and total compares
only books quoting the leg's own line. Consumer items (F01, F03) show `best_overall` for the two books reasons.

**Your books** are resolved in this order: the `books` parameter (at most 20 provider sportsbook keys, 422
`unknown_sportsbook` or `too_many_books` otherwise); the profile's books held once P0.4 exists (not built); the books
of your own recorded bets that match a provider sportsbook by name or key; none (`books_source: "none"`).

## Its data

Migration `0008_snapshot_archive.py` adds five tables and touches nothing else. Its downgrade drops them, which
deletes archive data only.

| Table | One row per | Unique key |
|---|---|---|
| `snapshot_runs` | capture or prune pass: counters, stale thresholds in force, archive version, `failed` detail (exception class name only) | id |
| `event_snapshots` | in-scope event per odds capture (also the coverage record) | `(provider, event_id, captured_at)` |
| `odds_snapshots` | (event, market, book), written only when the quote changed; a quote that disappears gets a tombstone row | `(provider, event_id, market, sportsbook_id, captured_at)` |
| `prop_snapshots` | (player, game, market, book), written only when the offer changed; once a game leaves scope each of its open offers gets a tombstone row | `(provider, player_id, event_id, market, sportsbook_id, captured_at)` |
| `status_snapshots` | lineup or news status record when it changed | — |

- Rows are never updated. A `before_flush` guard (`archive/guard.py`) rejects any ORM update or delete of an archive
  row; the only deletions are the retention prune's bulk deletes.
- `captured_at` is the provider clock and is shared by every row of one run. `run_id` is a plain integer, not a
  foreign key (a key without an index would make every run deletion scan the archive).
- Every read filters on the running provider's name, so replay and synthetic rows never mix.
- **No personal data.** The archive holds market data only. Bets are joined at read time and never copied in.
  Account export and deletion are unaffected.
- **Retention.** Full-resolution rows: 7 days (`ODDVEX_SNAPSHOT_RETENTION_DAYS`). The prune handles a game once,
  when all of its rows are older than that, so a quote carried forward unchanged is never lost for a time that is
  still within retention. Kept 400 days (`ODDVEX_SNAPSHOT_KEEP_DAYS`), with status rows and runs:
  - the **closing capture**: the game's last `upcoming` event row and, per market and book and per player offer, the
    latest row at or before it;
  - the **last capture**: the game's last event row and the latest odds row per market and book at or before it
    (it marks when the game left scope, and is a complete capture);
  - **bet anchors, bounded**: for stored bet legs the archive can price (moneyline, spread or total with an outcome
    and, for spread and total, a line), the capture that covered the bet's `placed_at`, with its odds rows. At most
    6 captures per game (`MAX_ANCHORS_PER_EVENT` in `archive/prune.py`), ranked by weight: every user with a bet on
    the game has one vote, split evenly over the captures that user's bets point at; ties go to the earlier capture.
    One user's bets, however many, never keep more than 6 captures of a game and weigh no more than another user's
    single bet. Each user is still one vote, so with a tie one user's earlier capture can take the last slot from
    another user's later one, and many accounts acting together could crowd others out; the disk bound holds either
    way. Unstructured legs keep nothing.

  A bet whose capture was not kept, or a bet recorded after its capture was pruned, answers `archive_pruned`.
  Every other row of the game goes, including prop rows captured after its last event row (the tombstones written
  when it left scope); those go up to about an hour before they are 7 days old, never later. The props read accounts
  for this (see "Coverage of a player's props at T").
- **Capture.** In scope: live games and games starting within 36 hours; a game still `upcoming` more than 6 hours
  after its start time (postponed, never updated by the provider) is dropped. Odds every 360 s (three turns of the
  120 s worker loop; a 15 s slack absorbs drift), props every 3,600 s, the prune hourly. An unchanged prop offer is
  stored again once its latest row is 24 hours old (`PROP_REFRESH_HOURS`), so the 48-hour props read still finds it
  for a game that stays in scope longer (one that keeps being pushed back). A PostgreSQL advisory lock
  stops two passes overlapping. Inserts go in chunks of 500, one transaction per kind; a failed kind is rolled back
  and recorded as a `failed` run, and the next turn tries again.

Settings (environment, `ODDVEX_` prefix): `SNAPSHOT_ODDS_INTERVAL_SECONDS` 360 (minimum 60),
`SNAPSHOT_PROPS_INTERVAL_SECONDS` 3600, `SNAPSHOT_HORIZON_HOURS` 36, `SNAPSHOT_RETENTION_DAYS` 7,
`SNAPSHOT_KEEP_DAYS` 400, `SNAPSHOT_MAX_BYTES` 1610612736 (1.5 GiB), `SNAPSHOT_MAX_GAP_SECONDS` 840,
`SNAPSHOT_PRUNE_INTERVAL_SECONDS` 3600.

## Bounds on the shared server

Measured on 2026-11-26 on PostgreSQL 16 in the throwaway test database, with the synthetic provider: 480 odds
passes and 48 props passes (two synthetic days), `VACUUM ANALYZE` and `pg_total_relation_size` (heap, keys and every
index), then a prune seven days on (a scratch measurement script, not product code).

| | rows (2 days) | bytes per row | bytes per day |
|---|---|---|---|
| `odds_snapshots` | 244,438 | 415 | 50.7 MB |
| `prop_snapshots` | 85,440 | 395 | 16.9 MB |
| `event_snapshots` | 15,440 | 349 | 2.7 MB |
| `snapshot_runs` | 528 | 388 | 0.1 MB |
| **total** | | | **70.4 MB** |

The prop key now includes the game (a few bytes more per row than the 359 measured for revision 2), and the first
pass of a run writes every quote, so the two-day figure is a little above steady state.

- **Full resolution.** The prune handles a game once all its rows are 7 days old, so rows wait on average 13.7 hours
  longer (byte-weighted, measured over the 38 complete games). That is about (7 + 0.57) × 70.4 MB = **0.55 GB after
  the first week**.
- **Kept 400 days.** One pruned game keeps its closing and last captures, props included: 40.1 kB on average (70
  games measured). At 20 games a day that is 0.8 MB a day, 0.32 GB by day 400, so **about 0.85 GB by day 400** with
  few bets.
- **Bet anchors, worst case.** One kept capture is at most 7.3 kB (an event row and 16.8 odds rows on average); 6
  per game is 43.9 kB, 0.88 MB a day, 0.35 GB by day 400. With every game at the bound, **about 1.2 GB by day 400**,
  0.4 GB under the cap. However many bets users record, they cannot fill the cap and stop capture on this schedule.
- **Cap.** Capture stops when the archive holds 1.5 GiB of data (`skipped_full` runs) and the prune keeps running.
  The size the cap checks is each table's row count times its bytes per row from the table above (`ROW_BYTES` in
  `archive/capture.py`; status rows, of which there are none yet, are counted at an estimated 400), on every
  database. It is not the file size: on PostgreSQL a delete followed by a plain VACUUM (what autovacuum does) makes
  the freed space reusable by later rows but does not shrink the files, so a file-size cap would never release after
  the prune. Measured again on two synthetic days of the same schedule (a scratch script): the counted size was
  140.8 MB and the files 140.9 MB; after the prune and a plain VACUUM the counted size was 3.0 MB and the files still
  140.9 MB; two more synthetic days on top then brought the counted size to 144.4 MB and the files to 167.3 MB (19%
  above the first peak, 1.16 times the counted size), so most of the freed space was reused. The archive's files
  stay near their largest size: with the overhead measured here, about 1.75 GiB (1.9 GB, under 2% of the shared
  disk) when the counted size is at the cap. Only a `VACUUM FULL`, which blocks reads and writes of the tables while it
  runs, returns the space to the disk; nothing runs one. The administrators' statistics show both figures (`approx_bytes`,
  `disk_bytes`). Counting the rows took 22 ms at 346,000 rows; at the cap (about 4 million rows) that is roughly a
  quarter of a second once per pass. The synthetic schedule has 20 games a day and about 32 in the 36-hour window.
  Everything above grows with the number of games: at about 38 games a day (few bets), or 27 (every game at the
  anchor bound), the 400-day total reaches the cap; capture then stops, and resumes once the prune has brought the
  counted size back under the cap. A real schedule in season can be busier (OQ-23).
- **Prop refresh.** Storing an unchanged offer again once a day added 31 prop rows over the two synthetic days
  (85,471 against 85,440), about 12 kB.
- **Backups.** The archive is in every dump. One synthetic day of archive tables was 4.5 MB with `pg_dump -Fc`
  (measured for revision 2; synthetic prices are repetitive, real ones may compress less), so about 30 to 50 MB per
  dump and up to about 1 GB across the 19 daily and pre-deploy dumps. Owner question OQ-23.
- **Worker memory** (256 MB limit). One pass holds at most about 2,400 provider records plus the latest stored row
  per key of the in-scope games (and of games with an offer in the last 48 hours, for prop tombstones). The
  measurement process peaked at 127 MB resident, Python and its libraries included; the slowest of the 480 passes
  took 1.42 s, measured while the test suite ran on the same machine. The prune holds one game's rows at a time
  (ids, keys and times of a few thousand rows) and the (user, placement time) of that game's structured bet legs,
  streamed 1,000 at a time; it deletes in batches of 1,000 with a commit each.
- **API memory** (768 MB limit). Every read is bounded to one event and market (one row per book), one player (one
  row per market and book of each game with an offer in the last 48 hours, two or three games at most), one event's
  status records (at most 500), or one bet's legs (at most 20). There is no list-all route.

## Limits

- **Live bets.** Live quotes go stale after 120 s (`ODDVEX_STALE_LIVE_SECONDS`) and captures are 6 minutes apart, so
  most live bets answer `cannot_price: stale_at_placement`. That is the honest answer under hard rule 3; a faster
  live cadence waits for a live data vendor (OQ-17).
- **No backfill.** Provider line history is generated, not recorded, so bets placed before capture started answer
  `not_captured`.
- **Props** are captured hourly. Their coverage status is read from the props captures, not per game: a game whose
  start moved so that it was out of scope at a capture still reads `captured` then, with none of its offers. After
  the prune a game's props are served only where its kept closing offers are still the answer. A game first captured
  already live has no closing capture and keeps no prop rows; after the prune it is listed in `pruned_event_ids` only
  through the player's current team (a player who changed teams since is not matched).
- **Coverage labels after the prune.** `archive_pruned` is given when R falls between the game's entry into scope
  and its last capture. If the provider briefly dropped the game from scope at R, the right label was
  `not_captured`; both answer `cannot_price`, so only the label differs.
- **The flag also stops the prune** (see "How to switch it on"): while it is off, stored rows outlive the 7- and
  400-day retention.
- **Status records** are stored only through `capture_status`, which nothing calls on a schedule until P0.5 supplies
  a lineup and news provider; P0.5's interface must produce `StatusRecord` or migrate the table.
- Line history, game logs and next events are not served from the archive (F17, F34).
- Partitioning, and leaving the archive out of backups, are not built.
- Web and mobile screens are not part of this item; F01, F03, F22 and F34 build on it.

## Flag and entitlement

- Flag `snapshot_archive`, default off everywhere. Off means the capture writes nothing and the user routes answer
  404 `feature_disabled`. The admin statistics route stays available.
- P0.1 is a foundation with no Tier, and P0.3 (entitlements) has not landed, so nothing is gated by plan. When P0.3
  lands, `archive.read` is to be enabled on every plan and each consumer item (F01, F03, F22, F34) gates its own
  surface with its own Tier. The existing, unused `odds_history_hours` entitlement is not applied to these routes;
  a limit on how far back a plan may query is a pricing decision (OQ-01).

## Hard rules

1. Nothing places, pre-fills or links to a wager; the responses carry no links.
2. Every archived row in a response carries its `captured_at`, and every user response carries `data_mode` and the
   time it answers for (`requested_as_of`, or `placed_at` for placement prices); the administrators' statistics
   carry run times only. No estimate is introduced.
3. Prices come only from stored quotes through `Board`; missing or uncertain inputs answer `cannot_price` with a
   named reason.
4. The archive is not an opportunity surface and sends nothing; consumer items call the P0.6 suppression hook.
5. Data comes only through the configured provider interface (synthetic here); nothing is scraped.
6. Nothing depends on state law.

Stop list: no item hit.

  for live bets, no backfill, and the bet-anchor budget (6 captures per game: bets beyond it answer `archive_pruned`

  until it is on again. Relevant to the licence question below.
- Counsel, before a real provider is connected (with OQ-02 and OQ-03): whether the data licence allows storing the
  vendor's prices and lineup or injury status for 7 and 400 days and serving them back as of a past time. Archival
  and display rights are often separate terms; the status table stores no editorial text for this reason.
