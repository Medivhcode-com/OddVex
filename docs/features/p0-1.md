# P0.1 Snapshot archive

Linear: MED-72. Flag: `snapshot_archive`, off by default (also in production). Entitlement: none yet (see below).
Design note: the design comment on MED-72, revision 6 (2026-11-26).

## What it does

Until now OddVex stored no market data: the board read the provider's current quotes on every request. The snapshot
archive keeps an append-only record of what the provider reported, so the app can answer "what did OddVex know at
time T?":

- every book's quote for every game market (moneyline, spread, total), with its status and `last_updated`;
- every book's player-prop offer;
- the event state that staleness depends on (status, start time, score, `score_updated_at`);
- the stale thresholds in force at each capture, which decide which quotes count toward best price and consensus;
- lineup, injury, news and weather status records, once a source exists (P0.5). Only a status, a source name and
  times are stored, never article or headline text.

Two reads are built on it:

1. **As of T.** `ArchiveView` (`services/api/src/oddvex_api/archive/view.py`) is a read-only data provider that
   answers only from rows captured at or before T. It is handed to the existing `Board`, so the best price and the
   no-vig consensus as of T come from the same, already tested code as the live board (`board.py`, `quant/`). Its
   staleness is judged at T with the thresholds stored on the capture run. One difference from the live board: a game
   archived as `upcoming` whose start time had passed at T is judged by the live threshold (120 s), so a pregame
   quote never passes as an in-play price; the game keeps the status it was captured with in every response.
2. **Placement-time prices.** For every leg of a stored bet, `placement_prices`
   (`archive/placement.py`) returns either `priced`, with the best price overall and the best price at the user's
   books as of the bet's `placed_at`, or `cannot_price` with a named reason.

No new calculation was added. The changes to `Board` are additive and leave the live board unchanged:
`best_price(..., books=...)` keeps only the user's sportsbooks; `quote_rows` is a public name for the rows `best_price`
and `event_odds` judge; `freshness_status(event)` names the status whose stale threshold applies (the event's own
status on the live board).

## How to switch it on

1. Turn the flag on: `PUT /v1/admin/flags/snapshot_archive` with `{"enabled": true}` (administrators only).
2. Capture: on the preview the worker container runs `python scripts/capture_snapshots.py` every 120 s
   (`infrastructure/hostinger/compose.yaml`). Locally there is no worker; run it by hand from `services/api`:

   ```bash
   .venv/bin/python scripts/capture_snapshots.py               # capture what is due, prune when due
   .venv/bin/python scripts/capture_snapshots.py --force       # capture now, whatever the intervals
   .venv/bin/python scripts/capture_snapshots.py --prune-only  # prune when due (with --force: now)
   .venv/bin/python scripts/capture_snapshots.py --dry-run     # what a pass would capture; writes nothing
   .venv/bin/python scripts/capture_snapshots.py --stats       # size, row counts, latest runs
   .venv/bin/python scripts/capture_snapshots.py --reclaim     # PostgreSQL: check the indexes now (see "Bounds")
   ```

While the flag is off the script prints "Snapshot archive is off; nothing captured." and writes nothing, so turning
the flag off stops all growth. It also stops the prune and the index reclaim: the rows already stored stay, past the
7- and 400-day retention, until the flag is on again and the next prune removes them. The only other way to remove
them is migration 0008's downgrade, which drops the five archive tables. The Founder and counsel should know this for
OQ-23 (e).

Before switching it on in the preview, read owner question OQ-23. The index rebuilds were run on PostgreSQL 16 on
the development machine only, and the preview is PostgreSQL 17 on a slower, shared disk (see "Index space"). Nothing
can be run by hand there (nobody has a shell on that server and no ops action runs a script), and `--reclaim` would
not help anyway: it only rebuilds an index that has already grown past 1.3 times the size its rows need, and on a
new archive none has ("reclaim: nothing to rebuild"). The first rebuild on the preview happens by itself after the
first prune that deletes rows, a little over 7 days after the flag is turned on. The check to make then: the
`reclaim` entry of `GET /v1/admin/archive/stats` should say `status: ok` with `indexes_rebuilt` above 0, and
`finished_at` less `captured_at` is how long the pass took. A failed one names the index and the class of the
error in `failed_indexes`. Until then PostgreSQL 17 is covered by the CI job "Snapshot archive on PostgreSQL 17"
only, which runs on the pull request for the first time. `infrastructure/hostinger/README.md` has the operator's
steps, and says how an archive setting is changed on the preview: a commit to `compose.yaml` and a deploy
(`ACTION=setenv` does not take these keys).

The script exits with status 2 and does nothing, and the application refuses to start, when the archive settings
cannot work together: a keep period (`ODDVEX_SNAPSHOT_KEEP_DAYS`, or the retention days when larger) no longer than
the props look-back (48 hours by default), with which no archived props read would ever answer. The application
checks this whether the flag is on or off, so a wrong archive setting stops the whole API from starting, not only
the archive: on the preview a deploy with such a value fails its health check and the previous release is put back.

## API

All routes are additive. The user routes need sign-in and answer `404 feature_disabled` while the flag is off.

| Route | What |
|---|---|
| `GET /v1/archive/events/{event_id}/odds?market=&as_of=` | The event's coverage at `as_of` and, only when it is `captured`, each book's stored quote from the covering capture and the odds comparison (`EventOddsOut`) as of `as_of` |
| `GET /v1/archive/players/{player_id}/props?as_of=&market=` | The props coverage at `as_of` and, when it is `captured`, the latest offer per game, market and book at or before `as_of`, for each of the player's games with an offer in the look-back before `as_of` (48 hours with the default settings); a game whose offers were all withdrawn or that had left scope (tombstones) is left out, and so is a game the prune has reduced to closing offers that are no longer the answer at `as_of` (listed in `pruned_event_ids`). A props capture holds the games of the odds capture made in the same pass |
| `GET /v1/archive/events/{event_id}/status?as_of=` | The latest status record per team or player and kind at or before `as_of` (empty until P0.5), with its coverage and the time from which records are kept (`kept_from`) |
| `GET /v1/bets/{bet_id}/placement-prices?books=` | Placement-time prices for each leg of your own bet; another user's bet answers 404 like a missing one |
| `GET /v1/admin/archive/stats` | Administrators only, not behind the flag: counted size and its cap, size of the files and their ceiling (PostgreSQL), row counts, latest run of each kind; a failed capture or prune shows the class name of its error (`error`); the latest `reclaim` run says when index space was last returned to the disk and how much, and names each index whose rebuild failed with the class of its error (`failed_indexes`). Audited as `admin.read` |

`as_of` must carry a time zone offset (422 `as_of_without_offset`) and may be at most 60 s past the provider's clock
(422 `as_of_in_future`). The odds, props and placement routes can answer 503 `archive_busy` with `Retry-After: 5`
(see "Reading beside the prune"); it is not expected in operation.

**Coverage of an event at T** is read from R, the latest successful odds capture at or before T:

- `captured`: R is at most 840 s before T (`ODDVEX_SNAPSHOT_MAX_GAP_SECONDS`: two odds intervals plus one worker
  turn, so one missed pass is tolerated and two are not) and the archive holds the event's row from R. Only then is
  anything priced, and always from R: an older kept capture never stands in for a pruned one. A capture the archive
  holds is whole: every quote it carried forward from an earlier capture is there (see "Retention");
- `archive_gap`: no successful odds capture within 840 s before T;
- `archive_pruned`: R ran while the game was in scope (between its first and its last capture, both of which are
  kept), but the game's rows from R were pruned; or T is within 840 s of the keep horizon or before it. Capture runs
  from before the keep horizon (400 days before the newest prune) are no longer all kept, so the archive cannot know
  which capture was the latest then and answers nothing from there;
- `not_captured`: before the first capture, or the game was not in scope at R (for example three days before it,
  or after it ended).

Quotes and the comparison are returned only when the status is `captured`: an older kept capture is not the market
at T.

**Coverage of a player's props at T** is read from P, the latest successful props capture at or before T:
`captured` when P is at most 7,320 s before T (two props intervals plus one 120 s worker turn), `archive_gap` when it
is older, `not_captured` before the first props capture, and `archive_pruned` when the look-back from T reaches
past the keep horizon. The look-back is how old an open offer's latest row can be: the capture horizon plus 12
hours for the game (48 hours by default), and never less than 24 hours plus the props gap limit, because an
unchanged offer is stored again only at the first props capture after its row is 24 hours old (see "Capture").
Offers are returned only when `captured`. After the prune a game keeps only its
closing offers (per offer, the latest row at or before its closing capture). Those are served for T only while they
are still the answer: from each kept offer's capture until the first props capture after the closing capture.
Otherwise the game's offers are left out and its id is listed in `pruned_event_ids`, for any T from the first props
capture that can have had the game (worked out from its kept first capture, so a start time moved later changes
nothing) to one look-back after the props capture that tombstoned its offers. A pruned game that later comes back into
scope (moved, then played) reads whole again from then on; its earlier stay stays pruned.

Which games the read checks is decided by the span of each game's event rows, from its first capture to its last
(the prune keeps both): every game the player has a prop row of, at any time, whose span reaches within a few
look-backs of T. A row near T is not needed, and after the prune there may be none: a game listed three times,
weeks apart (postponed twice under the same id), keeps its first capture and the closing and last captures of its
third stay, and nothing of the second. A time in the second stay is inside the span, so the game is named there.
(Review round 5 found the read choosing games by a row within a few days of T: for such a game it answered
`captured` for the second stay with none of the game's offers and without naming it, while the odds read at the
same time said `archive_pruned`.) Three rules make the choice complete:

- the prune keeps at least one prop row of every player who ever had an offer on a game: the closing offer, or,
  for an offer with no row at or before the closing capture (first offered once the game was in play, or a game
  never captured as `upcoming`), the offer's latest row as a marker (see "Retention"). So the player's own prop
  rows name every game the player had offers on. The player's team is no longer consulted;
- the prune keeps a game's first and last captures, so the span is what it was before the prune;
- an offer is only ever stored beside its game's event row of the same capture (see "Capture"), so a game that
  had an offer near T has T inside its span.

One consequence: a game listed several times is also named for times between its stays, when it had no offers at
all, wherever the kept closing offers are not the answer.

**Coverage of an event's status records at T**: `captured` when the archive holds a record of the event captured
at or before T (`entries` is then the latest of each team or player and kind), `not_captured` when it holds none,
`archive_pruned` when it holds none and T is before the keep horizon. A status record is stored when it changes and
kept 400 days; one that has not changed since before `kept_from` (the keep horizon, in the answer) is no longer
among the entries.

**Reading beside the prune.** The prune runs in the worker while the API answers, and it can be cut short at any
point (a deploy replaces the worker container, a connection drops, the database restarts). Three rules keep every
answer right at every such moment (review round 4 found the case where they were missing: a capture whose event
row was still there while its quotes were gone read as `captured` and was priced from an older capture):

- The prune records how far it will go before it deletes anything: a `prune` run with status `started` and both
  cutoffs, committed first. From then on the reads treat every game and time it may reach as reduced, whether the
  prune has got there, is still running or was cut short. It writes its `ok` run (or a `failed` one) at the end,
  and the next prune starts from the last `ok` one, so what a cut-short prune left is done then (the next worker
  turn: a prune that did not finish does not count as the hourly prune).
- A game's rows go in one transaction: its event rows (the coverage record), odds rows and prop rows together, at
  the 7-day reduction and at the keep horizon. No committed state holds a capture without its quotes; a prune that
  stops inside a game leaves that game as it was.
- A read checks itself. It is several statements, and on PostgreSQL each sees what was committed when it began, so
  a game's transaction can land between two of them. After its last statement an odds, props or placement read
  checks that no prune has started since its first and that every capture it answered from is still held; if not
  it is made again, at most four times in all, then 503 `archive_busy`. For one game one prune can disturb a read
  three times at most (it starts, it reduces the game, the keep horizon removes the game), and two prunes are at
  least a worker turn (120 s) apart, so the odds and props reads do not give up in operation. The placement prices
  of a parlay read every leg's game again on each attempt: a prune that reduces a different leg's game during each
  attempt can use the four up (from the code, not reproduced). The answer is then the 503 with `Retry-After`,
  never a price.

A capture can also commit between two statements of a read as of "now". The coverage read takes the covering
capture first and the game's row second, so it answers either from the capture before or, whole, from the new
one. (Read the other way round, as it was until review round 5, a game in scope answered `not_captured` for that
one request; a test now commits a capture between the two statements.) An answer for a time in the last few
seconds can still change once the pass that was running then has committed: a capture is stamped with the
provider's clock when the pass begins and is visible when it commits.

While a prune that was cut short waits for the next one, a game it had not reached is whole but read as reduced:
its odds answer as before, and its props are served only where the kept closing offers would be the answer.

**A leg's answer** is `priced` (best price at your books found) or `cannot_price` with `reason`:

- `leg_not_structured`: the leg has no event, no outcome, a market other than moneyline, spread or total, or no line
  for a spread or total (for example a typed player prop);
- a coverage status: `not_captured`, `archive_gap`, `archive_pruned`;
- `stale_at_placement`: open, fully priced quotes for the outcome existed, but every one was stale at `placed_at`
  (including a pregame quote for a bet placed after the start time, judged by the 120 s live limit);
- `no_usable_quote`: no open quote for the outcome on the leg's line;
- `none_at_your_books` or `books_unknown`: a price existed, but not at your books, or no books are known for you.
  `best_overall` then holds that price, and `your_books_reason` carries the same value.

`reason` is null only when the leg is `priced`. The best price uses the latest capture at or before `placed_at`,
judges staleness at `placed_at`, excludes stale, suspended and unavailable books, and for spread and total compares
only books quoting the leg's own line. Consumer items (F01, F03) show `best_overall` for the two books reasons.

**Your books** are resolved in this order: the `books` parameter (at most 20 provider sportsbook keys, 422
`unknown_sportsbook` or `too_many_books` otherwise); the profile's books held once P0.4 exists (not built); the books
of your own recorded bets that match a provider sportsbook by name or key; none (`books_source: "none"`).

## Its data

Migration `0008_snapshot_archive.py` adds five tables and touches nothing else. Its downgrade drops them, which
deletes archive data only.

| Table | One row per | Unique key |
|---|---|---|
| `snapshot_runs` | capture, prune or index-reclaim pass: counters, stale thresholds in force, archive version, how far a prune goes (`prune_cutoff`, `keep_cutoff`), `failed` detail (exception class name only), a reclaim's index names and byte counts. A prune writes two rows: `started`, before it deletes anything, and `ok` or `failed` at its end | id |
| `event_snapshots` | in-scope event per odds capture (also the coverage record) | `(provider, event_id, captured_at)` |
| `odds_snapshots` | (event, market, book), written only when the quote changed; a quote that disappears gets a tombstone row | `(provider, event_id, market, sportsbook_id, captured_at)` |
| `prop_snapshots` | (player, game, market, book), written only when the offer changed; once a game leaves scope each of its open offers gets a tombstone row | `(provider, player_id, event_id, market, sportsbook_id, captured_at)` |
| `status_snapshots` | lineup or news status record when it changed | — |

- Rows are never updated. A `before_flush` guard (`archive/guard.py`) rejects any ORM update or delete of an archive
  row; the only deletions are the retention prune's bulk deletes.
- `captured_at` is the provider clock and is shared by every row of one run. `run_id` is a plain integer, not a
  foreign key (a key without an index would make every run deletion scan the archive).
- Every read filters on the running provider's name, so replay and synthetic rows never mix.
- **No personal data.** The archive holds market data only. Bets are joined at read time and never copied in.
  Account export and deletion are unaffected.
- **Retention.** Full-resolution rows: 7 days (`ODDVEX_SNAPSHOT_RETENTION_DAYS`). The prune handles a game once,
  when all of its rows are older than that, so a quote carried forward unchanged is never lost for a time that is
  still within retention. Its last event row says when that is: an open prop offer is never stored later than
  its game's last event row (see "Capture": a props capture takes a game only with the odds capture of the same
  pass). The reads work out the same thing from the same rows. Kept 400 days (`ODDVEX_SNAPSHOT_KEEP_DAYS`):
  - the **first capture**: the game's first event row and its odds rows. It marks when the game entered scope,
    whatever its start time was then or became later, and it is the opening quote of every book;
  - the **closing capture**: the game's last `upcoming` event row and, per market and book and per player offer, the
    latest row at or before it. A player offer with no row that early keeps its latest row instead (usually the
    tombstone written when the game left scope). That row is a marker for the props read, never an answer (round
    6; before, such an offer kept nothing, and a game first captured already live kept no prop row at all).
    Measured on the synthetic schedule over eight synthetic hours (39 games): 264 marker rows, all of the two
    games that were already live when capture began (132 offers each, 52 kB a game as the cap counts it); none
    for the 37 games captured from before their start. So the figures under "Bounds" stand, with a one-time
    104 kB when capture starts;
  - the **last capture**: the game's last event row and the latest odds row per market and book at or before it
    (it marks when the game left scope, and is a complete capture);
  - **bet anchors, bounded**: for stored bet legs the archive can price (moneyline, spread or total with an outcome
    and, for spread and total, a line), the capture that covered the bet's `placed_at`, with its odds rows. At most
    6 captures per game (`MAX_ANCHORS_PER_EVENT` in `archive/prune.py`), ranked by weight: every user with a bet on
    the game has one vote, split evenly over the captures that user's bets point at; ties go to the earlier capture.
    One user's bets, however many, never keep more than 6 captures of a game and weigh no more than another user's
    single bet. Each user is still one vote, so with a tie one user's earlier capture can take the last slot from
    another user's later one, and many accounts acting together could crowd others out; the disk bound holds either
    way. Unstructured legs keep nothing.

  A bet whose capture was not kept, or a bet recorded after its capture was pruned, answers `archive_pruned`.
  Every other row of the game goes, in one transaction per game (see "Reading beside the prune"), including prop
  rows captured after its last event row (the tombstones written when it left scope); those go up to about an hour
  before they are 7 days old, never later. The props read accounts for this (see "Coverage of a player's props at
  T").
- **The keep horizon works per game.** A kept capture holds rows older than itself: a quote unchanged since an
  earlier capture is stored once, at that earlier capture. So a game's event, odds and prop rows leave together,
  once its last capture is 400 days old; until then every kept capture of it is whole, and the oldest of its rows
  is older than 400 days by the time the game was captured for. That is usually the 36 hours before its start
  and the game itself, but it has no fixed upper bound: a game is captured for as long as the provider lists it
  inside the scope rule below, so one whose start keeps being moved stays, and one that is listed again later
  (postponed, then played weeks on) keeps the kept rows of its first stay until its last capture is 400 days old.
  A status row goes by its own age. A capture run past the horizon is deleted only when no remaining row refers to it; the
  last successful odds and props capture before the horizon also stays, so a later time with no capture since
  still reads as a gap. Each prune records how far it goes (`prune_cutoff`, `keep_cutoff`), when it starts and
  again when it ends; neither ever moves back, so raising a retention setting later cannot make a read trust what
  an earlier prune removed. Status rows, rows of a game without an event row and capture runs past the horizon go
  in batches of 1,000 with a commit each. The odds and props reads answer nothing from before the horizon once
  the prune has started. The status read serves the records it holds whatever their age (with `kept_from`), so
  the batches go oldest first: stopped between two of them, what is left of a subject is its newest records,
  never an older one in place of a newer. (Until review round 5 the batches had no order; on PostgreSQL a sweep
  cut after its first batch could leave a subject's older record and serve it as the latest. Nothing writes
  status rows until P0.5.)
- **Capture.** In scope: live games and games starting within 36 hours. A game still `upcoming` more than 6 hours
  after its start time (postponed, never updated by the provider), or still `live` more than 24 hours after it
  (finished, never updated), is dropped: without the second rule such a game would never leave scope, the prune
  would never reduce it, and it would grow at full resolution until the cap stopped capture for every game. Odds
  every 360 s (three turns of the 120 s worker loop; a 15 s slack absorbs drift), props every 3,600 s, the prune
  hourly, and on PostgreSQL the index check after each prune (see "Index space"). **Props are never captured
  without the odds capture of the same pass.** When the props are due the pass captures odds too, first, even if
  the odds interval has not passed (the next odds capture is then counted from that one, so this moves an odds
  capture more often than it adds one), and the props capture takes exactly the games that odds capture wrote an
  event row for. If the odds capture fails, the pass ends and the props are tried again on the next turn. So
  every open prop row has its game's event row of the same capture time beside it, and the prune and the reads
  can tell from a game's event rows alone when it can have had offers. Before review round 5 a props capture
  took the games the provider listed at that moment: a game listed for one pass in which only props were due got
  prop rows that no event row placed, the prune later deleted them, and the read of that moment answered
  `captured` without them. An unchanged prop offer is stored
  again at the first props capture after its latest row is 24 hours old (`PROP_REFRESH_HOURS`). A read is answered
  from a props capture up to the gap limit before T, so an open offer's latest row is always less than 24 hours
  plus that limit old, and the read's look-back is never shorter than that, at any allowed setting. (Until review
  round 4 it was the horizon plus 12 hours only: with a horizon of 14 hours or less an offer unchanged for a day
  dropped out of a `captured` answer until the next props capture.) A PostgreSQL advisory lock stops two passes
  overlapping. Inserts go in chunks of 500, one transaction per kind; a failed kind is rolled back
  and recorded as a `failed` run, and the next turn tries again.

Settings (environment, `ODDVEX_` prefix): `SNAPSHOT_ODDS_INTERVAL_SECONDS` 360 (minimum 60),
`SNAPSHOT_PROPS_INTERVAL_SECONDS` 3600, `SNAPSHOT_HORIZON_HOURS` 36, `SNAPSHOT_RETENTION_DAYS` 7,
`SNAPSHOT_KEEP_DAYS` 400, `SNAPSHOT_MAX_BYTES` 1610612736 (1.5 GiB, the counted cap), `SNAPSHOT_MAX_DISK_BYTES`
2147483648 (2 GiB, the ceiling on the files, PostgreSQL only), `SNAPSHOT_MAX_GAP_SECONDS` 840,
`SNAPSHOT_PRUNE_INTERVAL_SECONDS` 3600, `SNAPSHOT_RECLAIM_TIMEOUT_SECONDS` 120 (how long one index rebuild may
take, PostgreSQL only). The keep period must be longer than the props look-back (see "How to switch it on").

## Bounds on the shared server

Measured on 2026-11-26 on PostgreSQL 16 in the throwaway test database, with the synthetic provider: 480 odds
passes and 48 props passes (two synthetic days), `VACUUM ANALYZE` and `pg_total_relation_size` (heap, keys and every
index), then a prune seven days on (a scratch measurement script, not product code).

| | rows (2 days) | bytes per row | bytes per day |
|---|---|---|---|
| `odds_snapshots` | 244,438 | 415 | 50.7 MB |
| `prop_snapshots` | 85,440 | 395 | 16.9 MB |
| `event_snapshots` | 15,440 | 349 | 2.7 MB |
| `snapshot_runs` | 528 | 388 | 0.1 MB |
| **total** | | | **70.4 MB** |

The prop key now includes the game (a few bytes more per row than the 359 measured for revision 2), and the first
pass of a run writes every quote, so the two-day figure is a little above steady state.

- **Full resolution.** The prune handles a game once all its rows are 7 days old, so rows wait on average 13.7 hours
  longer (byte-weighted, measured over the 38 complete games). That is about (7 + 0.57) × 70.4 MB = **0.55 GB after
  the first week**.
- **Kept 400 days.** One pruned game keeps its first, closing and last captures, props included: 50.2 kB on
  average (630 games over nine prune cycles, measured again in round 4 with the first capture kept; 40.1 kB before).
  At 20 games a day that is 1.0 MB a day, 0.40 GB by day 400, so **about 0.95 GB by day 400** with few bets.
- **Bet anchors, worst case.** One kept capture is at most 7.3 kB (an event row and 16.8 odds rows on average); 6
  per game is 43.9 kB, 0.88 MB a day, 0.35 GB by day 400. With every game at the bound, **about 1.3 GB by day 400**,
  0.3 GB under the cap. However many bets users record, they cannot fill the cap and stop capture on this schedule.
- **Cap (counted data).** Capture stops when the archive holds 1.5 GiB of data (`skipped_full` runs) and the prune
  keeps running. The size the cap checks is each table's row count times its bytes per row from the table above
  (`ROW_BYTES` in `archive/capture.py`; status rows, of which there are none yet, are counted at an estimated 400),
  on every database. It falls as soon as the prune deletes rows, so capture resumes then. Counting the rows took
  22 ms at 346,000 rows; at the cap (about 4 million rows) that is roughly a quarter of a second once per capture
  pass, with the tables in memory. Review round 5 measured 0.15 to 0.5 s at 3.3 to 3.7 million odds rows, by an
  index-only scan or a sequential scan of the whole table depending on how recently it was vacuumed, also in
  memory. The preview's database has 512 MB for a table of about 1 GiB at the cap, so there the count will read
  the disk and take longer; nobody has measured it there. The hourly reclaim plan and the statistics route count
  the same rows. The
  synthetic schedule has 20 games a day and about 32 in the 36-hour window. Everything above grows with the number
  of games: at about 34 games a day (few bets), or 25 (every game at the anchor bound), the 400-day total reaches
  the cap. A real schedule in season can be busier (OQ-23).
- **The files on PostgreSQL.** What is on the disk is the tables and their indexes (`pg_total_relation_size`,
  `disk_bytes` in the administrators' statistics), not the counted size. Two things are true of them:
  - *Table files never shrink.* A delete followed by a plain VACUUM (what autovacuum does, once a fifth of a
    table's rows are dead or new; see "Index space") makes the freed space reusable by later rows but does not
    return it to the disk. So the table files stay at the largest size the
    data has had; later rows fill the gaps (measured: over nine prune cycles the tables grew from 85.8 MB to
    103.2 MB while the counted size at each peak grew from 140.8 MB to 171.0 MB, the same share of it).
  - *Index files grew with every prune, until round 4.* The prune keeps a few rows of each finished game. In an
    index those entries are scattered over the game's old pages; a page is reused only when it is completely empty,
    so each pruned game left pages that were nearly empty, never empty, and never filled again. Review round 3
    measured it: indexes of 55.2, 80.0, 103.7, 127.5, 151.7 and 174.7 MB after six cycles of two synthetic days,
    and files of 270.0 MB for 18.1 MB of counted data. The counted cap cannot see that.
- **Index space** (`archive/reclaim.py`, PostgreSQL only). After each successful prune, and on every capture that
  finds the files over the ceiling, the pass compares each archive index with the size its rows need (measured
  bytes per row, `INDEX_ROW_BYTES`) and rebuilds the ones larger than 1.3 times that, by more than 1 MiB, with
  `REINDEX INDEX CONCURRENTLY`, one at a time. A rebuilt index is dense and the old file is removed, so the space
  really returns to the disk. An index is rebuilt at most once in 24 hours unless the files are over the ceiling,
  and one whose rebuild failed is left alone for 6 hours (1 hour while the files are over the ceiling), so a
  rebuild that cannot finish on this server does not write and discard a full copy after every prune.
  - **The stated factor: at its largest the files are within 1.25 times the largest counted size the archive has
    held** (`STATED_FILES_FACTOR`). Measured with the round-3 schedule repeated for nine cycles after the fix
    (`tests/measure_archive_files.py cycles 9`): at the nine peaks the files were 0.989 to 1.010 times the largest
    counted size so far (169.1 MB of files for 171.0 MB counted at the ninth peak), and after each prune the
    indexes were 3.3 to 13.0 MB instead of growing by 24 MB a cycle. In rolling operation (the worker's pass every
    360 s, retention shortened to one day and the keep period to three so the archive reaches its steady state)
    the result depends on how often the tables are vacuumed:
    - *With a VACUUM after every hourly prune* (`tests/measure_archive_files.py rolling 8`, eight synthetic days):
      the counted size settled near 130 MB and the files moved between 127 and 148 MB, at most 1.13 times the
      counted size, with 20 reclaim runs. A server does not vacuum that often.
    - *Vacuumed as a server with the default settings does* (`tests/measure_archive_files.py autovacuum 10`;
      the measurement review round 4 asked for): autovacuum takes a table only once its dead rows exceed 50 plus
      a fifth of its rows, or the rows inserted since its last vacuum exceed 1,000 plus a fifth
      (`autovacuum_vacuum_scale_factor` and `autovacuum_vacuum_insert_scale_factor`, 0.2 in the 16 and the 17
      manuals). The script counts both after every pass and vacuums then, and samples the sizes after every pass.
      Over ten synthetic days the counted size settled between 124 and 135 MB. The files reached 1.215 times the
      largest counted size so far (on day 5), with 32 reclaim runs, none failed; a pass that rebuilt took 0.9 to
      2.2 s. The stated factor, which is against the largest counted size, held at 1.215, with little margin.
      (Review round 4, with its own script, saw 1.22 and 1.24 in two runs; review round 5, on two other synthetic
      schedules of ten days each, 1.216 and 1.215.) Against the counted size of the moment, which falls after
      every prune while the table files stay, the ratio is higher: 1.272 here on day 8, and 1.308 and 1.282 in
      the round-5 runs. That ratio is not what the factor states and is not a bound on anything.

    After a large prune the files stay near that largest size while the counted size falls (the table files do
    not shrink); what the factor rules out is growth beyond it, prune after prune. With the counted size at its
    cap the files are therefore at most 1.25 × 1.5 GiB = 1.9 GiB if the factor holds, and under default
    autovacuum that is also about where to expect them (the measured 1.215 to 1.24 times 1.5 GiB is 1.82 to
    1.86 GiB), not the 1.7 GiB the every-prune figure suggested. The factor is a statement about what was
    measured, with a margin of a few hundredths; the 2 GiB ceiling is the stop that holds, with little room above
    the measured files. (An earlier revision gave "1.82 to 1.91 GiB" by multiplying the cap by the ratio to the
    counted size of the moment; with the round-5 ratios the same arithmetic gives 1.92 to 1.96 GiB. Neither is a
    file size anyone measured: at the cap the counted size of the moment is the largest.) Nobody has measured
    rolling
    operation at the production retention of 7 and 400 days (it would take 400 synthetic days); the shortened run
    has the same mechanism and a far larger share of rows turning over per day. Lowering the two scale factors for
    the three large tables would bring the every-prune figure within reach; it is not done here because it has not
    been measured (OQ-23).
  - **Locks.** `REINDEX INDEX CONCURRENTLY` holds `SHARE UPDATE EXCLUSIVE` on the table and the index and nothing
    stronger: reads, inserts and deletes go on (tested: a read and an insert go through while a rebuild waits);
    only a VACUUM of that table and schema changes wait for it, and an autovacuum of that table that is in its way
    is interrupted and starts again later (both manuals say so). It is never started beside a capture or a
    prune: it runs inside the capture pass, under the pass's advisory lock, after both have committed. One
    exception, which is safe: when the worker is killed while a rebuild runs (a deploy replaces the container),
    the database server finishes the rebuild on its own and the advisory lock goes with the dead connection, so
    the next pass can capture while that rebuild is still running; a concurrent rebuild is made to run beside
    writes, and review round 4 saw the next pass capture, wait for the rebuild and find nothing left to clean
    up. It cannot run inside a transaction: it uses its own connection in autocommit mode, checks that before
    every statement, and PostgreSQL
    refuses it in a transaction block as well.
  - **Waiting and time.** A rebuild waits for transactions older than itself (a dump in progress, a long report).
    It gives up after 10 s of waiting (`lock_timeout`) and after 120 s in all (`statement_timeout`, the setting
    `ODDVEX_SNAPSHOT_RECLAIM_TIMEOUT_SECONDS`); a pass starts no new rebuild after 60 s and stops at its first
    failure, and the failed index is then left alone for 6 hours (1 hour over the ceiling) unless
    `--reclaim` asks. The 120 s is about eight times what the largest index took here, with the whole table in
    memory. The preview's database has 512 MB and a shared disk, and at the cap the table does not fit in what is
    left for its cache: review round 5 estimated about 3.5 GB of disk reads and writes for one rebuild of the
    largest index, 35 to 70 s at 50 to 100 MB/s, so the margin there is nearer two times than eight, and nobody
    has timed it. A rebuild that exceeds the limit is recorded as failed with the error class `QueryCanceled`
    (in `failed_indexes` of the statistics and in the script's line), is tried again after 6 hours, and writes
    and discards about 0.5 GiB each time; the setting is then raised with a commit to
    `infrastructure/hostinger/compose.yaml` and a deploy. While a dump holds the tables (review round 4 held them with a transaction like
    `pg_dump`'s, at the size of the cap) every pass waits 10 s, records a failed reclaim and the script exits 1,
    so the worker log says "capture_snapshots failed" every two minutes until the dump ends; one extra copy of
    the index being rebuilt (256 MB there) stays on the disk meanwhile, and the first pass after the dump drops
    it. Captures and reads go on throughout. A pass that rebuilds also delays the worker's next alert evaluation
    and pick grading by its length (seconds here; by the constants at most about three minutes), at most about
    once an hour. Measured here: every index of two synthetic days
    (244,438 odds rows) rebuilt in 1.3 s together; at the size of the cap (3.3 million generated odds rows,
    `maintenance_work_mem` 32 MB, no parallel workers) the largest index, the odds key, took 14.5 s to go from
    416 MB to 256 MB, the primary key 2.1 s, the capture-time index 2.5 s. The passes that rebuilt something in the
    rolling run took 1.1 to 2.3 s.
  - **Extra disk and memory while it runs.** One index at a time: the new copy, the sort's temporary files and
    about one copy of write-ahead log. At the size of the cap, for the odds key: 256 MB of new index, 265 MB of
    temporary files and 232 MB of write-ahead log, for 14.5 s; the old 416 MB file goes when it ends. On the two
    synthetic days: 19 MB of new index. Memory: `maintenance_work_mem` is set to 32 MB for the rebuild (the
    database container has 512 MB) and parallel workers are off, so it uses one core.
  - **Interrupted.** A rebuild that is cancelled, that times out or whose database session is ended (the
    database restarts, the connection drops, an administrator terminates it) leaves an invalid index named
    `<index>_ccnew` beside the working one, or `<index>_ccold` when it failed after the new index had taken over.
    Nothing is unusable: queries ignore it and the working index stays valid (tested), but inserts still maintain
    it and its file counts in `disk_bytes`. Every pass of the script (every 120 s while the flag is on), including
    one whose capture or prune failed, looks for invalid indexes on the archive tables and drops them with
    `DROP INDEX CONCURRENTLY` before anything is rebuilt; while one cannot be dropped yet (the older transaction is
    still open) nothing is rebuilt, so at most one exists. A pass whose capture or prune failed rebuilds nothing.
    Killing the worker does not interrupt a rebuild: the server finishes it (see "Locks").
  - **Recorded.** A pass that rebuilt, dropped or failed writes a `reclaim` run: the index names, their sizes
    before and after, and the bytes returned. `GET /v1/admin/archive/stats` and `--stats` show the latest one
    (`indexes_rebuilt`, `indexes_dropped`, `indexes_failed`, `bytes_freed`, `finished_at`, and since round 6
    `failed_indexes`: each failed index with the class name of its error, which the script's own line prints as
    well). A failed one makes the
    script exit 1, so the worker log says so. That includes a rebuild whose database session was ended: until
    review round 4 that case ended the script with a traceback and no record (tested now by terminating the
    rebuild's backend). Three things the record does not show exactly: a rebuild the server finished after the
    worker was killed is in no run; one that failed after the new index took over is recorded as failed although
    the index was rebuilt, and the old copy's size is counted as freed when a later pass drops it; and when the
    database cannot be reached at all there is nowhere to record anything. Also seen in review round 5: after a
    worker was killed during a rebuild that the server then finished, the next pass recorded the finished
    rebuild's copy as dropped although nothing was there to drop (cosmetic; not changed). When the database ends
    the pass's own session (every backend terminated, as a restart does), the pass used to end with a traceback
    while releasing its advisory lock; it now logs that and returns what it did (tested on PostgreSQL 16).
  - **On SQLite** (local development) all of this does nothing: no statement is sent, no run is written, and
    `disk_bytes` is null (tested).
- **Ceiling (the files).** On PostgreSQL capture also stops while the files are at `ODDVEX_SNAPSHOT_MAX_DISK_BYTES`,
  2 GiB, whatever the counted size: a hard ceiling above the 1.9 GiB the stated factor allows at the counted cap.
  It releases when space has really been returned: the pass that finds the files over it rebuilds every index
  larger than 1.1 times its dense size, and the next capture runs (tested in both directions: the prune and a plain
  VACUUM alone leave the files as large and capture stopped, which was the round-2 finding; the rebuild brings
  them under and capture resumes). While a rebuild runs the files can be over the ceiling by that one index's new
  copy. The ceiling cannot release if it is set below the size of the table files themselves, which only a
  `VACUUM FULL` shrinks (it blocks reads and writes of the table while it runs; nothing runs one): keep it above
  the counted cap. Review round 5 set it below the table files: `skipped_full` runs on every pass, no rebuild
  loop, and no other signal. The settings check does not refuse such a value (a refused setting stops the whole
  API from starting, flag on or off, and that check is kept to the one combination that can never work).
- **PostgreSQL 17** (the preview runs `postgres:17-alpine`; this machine and CI run 16). The `REINDEX`, `DROP INDEX`
  and explicit-locking pages of the 16 and 17 manuals were compared (the Ubuntu `postgresql-doc-16` and
  `postgresql-doc-17` packages): the concurrent rebuild's steps, its `SHARE UPDATE EXCLUSIVE` lock, the invalid
  `_ccnew` and `_ccold` indexes an interrupted one leaves and how to recover, and the rule that it cannot run in a
  transaction block are word for word the same. Two differences, neither of which changes anything here: on 17 the
  right to rebuild comes from the `MAINTAIN` privilege on the table, which its owner has (on 16, from owning it;
  the application role owns the archive tables on both, because its migrations create them); and 17 sets
  `search_path` to `pg_catalog, pg_temp` while `REINDEX` or `VACUUM` runs, which matters only to indexes on
  expressions that call functions (the archive has none). The mechanism was run on 16 only; 17 was not available
  on this machine. CI now has a job that runs the archive and migration tests on `postgres:17`; it has not run
  yet (it runs on the pull request), so until it has, 17 is covered by the manuals only.
- **Prop refresh.** Storing an unchanged offer again once a day added 31 prop rows over the two synthetic days
  (85,471 against 85,440), about 12 kB.
- **Backups.** The archive is in every dump. One synthetic day of archive tables was 4.5 MB with `pg_dump -Fc`
  (measured for revision 2; synthetic prices are repetitive, real ones may compress less), about 34 MB for the
  7.6 days held at full resolution. The kept data adds to that: review round 4 dumped the kept rows of 700 pruned
  games (35.1 MB counted) to 2.29 MB, which makes about 26 MB for the 8,000 games of 400 days. So about 60 MB a
  dump by day 400 and about 1.15 GB across the 19 daily and pre-deploy dumps (the earlier text said 30 to 50 MB
  and 1 GB), and by the same arithmetic nearer 100 MB a dump with the counted size at the cap. A dump holds
  rows, not indexes or free
  space, so it follows the counted size. Owner question OQ-23.
- **Deploy, rollback and restore** (`infrastructure/hostinger/README.md`). A deploy replaces the worker: a capture
  or prune in progress is rolled back to its last commit (a prune per game, see "Reading beside the prune") and
  the next pass goes on. A rollback to an image from before P0.1 changes no table, but that image has no capture
  script: nothing captures, prunes or rebuilds until a newer image runs again, so rows outlive their retention and
  the time reads as an archive gap. A restore loads the dump into a new database (dense tables and indexes;
  captures made after the dump are gone, a gap) and keeps the replaced database in the server as
  `oddvex_replaced_<time>`, which no ops action removes: with the archive at its cap that is up to about 1.9 GiB
  more on the shared disk per restore, outside the archive's ceiling, until an action to drop one exists
  (OQ-23).
- **Worker memory** (256 MB limit). One pass holds at most about 2,400 provider records plus the latest stored row
  per key of the in-scope games (and of games with an offer in the last 48 hours, for prop tombstones). The
  measurement process peaked at 127 MB resident, Python and its libraries included; the slowest of the 480 passes
  took 1.42 s, measured while the test suite ran on the same machine. The prune holds one game's rows at a time
  (ids, keys and times of a few thousand rows) and the (user, placement time) of that game's structured bet legs,
  streamed 1,000 at a time; it deletes a game's rows 1,000 ids per statement in one transaction per game
  (measured in two cycles of two synthetic days: 337,138 and 338,557 rows of 70 games, deleted in 70 transactions of about 4,800 rows each, inside passes of 9.3 and 8.1 s that also rebuilt six and eight indexes, so about 0.1 s a game). The keep-horizon sweep holds one game's row ids and the ids of the capture runs older than the
  horizon. The index rebuild is the database's work,
  not the worker's.
- **API memory** (768 MB limit). Every read is bounded to one event and market (one row per book), one player (one
  row per market and book of each game with an offer in the last 48 hours, two or three games at most; once a
  prune has run, the ids of the games the player has a prop row of, a few hundred over 400 days, and of those
  the ones whose first-to-last captures span a time near T; and for each of these the capture times of its event
  rows, a few dozen once it is pruned. Measured on PostgreSQL 16 with generated rows at the size of the cap on
  the synthetic schedule, in memory (132,320 event rows, 118,080 prop rows, 266 games of the player; see
  "Tests"): the two statements that choose the games took MEASURED_CANDIDATES), one event's status
  records (at most 500), or one bet's legs (at most 20). Each read also takes the two cutoffs from the prune runs
  with one aggregate query (two prune runs an hour, 19,200 at day 400), and reads the id of the newest prune start
  before and after. A read that a prune disturbed is made again, at most four times in all, so the bound on rows
  read is four times the above. There is no list-all route.

## Limits

- **Live bets.** Live quotes go stale after 120 s (`ODDVEX_STALE_LIVE_SECONDS`) and captures are 6 minutes apart, so
  most live bets answer `cannot_price: stale_at_placement`. That is the honest answer under hard rule 3; a faster
  live cadence waits for a live data vendor (OQ-17).
- **No backfill.** Provider line history is generated, not recorded, so bets placed before capture started answer
  `not_captured`.
- **Props** are captured hourly. Their coverage status is read from the props captures, not per game: a game whose
  start moved so that it was out of scope at a capture still reads `captured` then, with none of its offers. After
  the prune a game's props are served only where its kept closing offers are still the answer. A game first captured
  already live has no closing capture, so none of its offers is served after the prune; it is listed in `pruned_event_ids`
  through the marker rows the prune keeps for it (each offer's latest row), so it is named for the player
  whatever team the player is on now. A game listed several times
  is named as pruned for times between its stays as well, when it had no offers, wherever its kept closing offers
  are not the answer. For one look-back (48 hours by default) after the keep horizon, and before it, the props
  read answers `archive_pruned`; with the capture rule of round 6 the gap limit would be enough there, and the
  wider refusal is kept as the cautious choice.
- **Props wait for the odds capture.** A props capture takes the games of the odds capture made in the same pass,
  and there is none without it. While the odds feed fails, props are not captured either (that was already so:
  a failed odds capture ends the pass), and a props read later answers `archive_gap` for that time.
- **Coverage labels after the prune.** `archive_pruned` is given when R falls between the game's first and last
  captures and at or before the time up to which the prune has reduced the game. If the provider briefly dropped the
  game from scope at R, the right label was `not_captured`; both answer `cannot_price`, so only the label differs.
- **A prune that was cut short.** Until the next prune finishes its work (the next worker turn), a game the cut
  prune had not reached is whole but is read as reduced: a capture at which the provider had briefly dropped it
  answers `archive_pruned` instead of `not_captured`, and its props are served only where the kept closing offers
  would be the answer, with the game named in `pruned_event_ids` otherwise. Nothing wrong is served; some answers
  are refused for those two minutes. A prune that fails on every turn writes two small runs per turn (its start
  and its failure), about 0.56 MB of counted data a day, which the counted cap does not stop.
- **A game that stays in scope.** A game is captured for as long as the provider lists it inside the scope rule:
  36 hours before its start, 6 hours after it while `upcoming`, 24 hours after it while `live`. A provider that
  keeps moving a game's start keeps it in scope, at full resolution, with no fixed end; the prune reduces a game
  only once its last capture is 7 days old.
- **Equal best prices.** When two books offer the same best price, the live board names the first in the order the
  provider returned the quotes; the archive returns quotes in the provider's sportsbook order. The synthetic
  provider returns them in that order too, so the two agree; a feed that orders quotes differently could name a
  different book on an exact tie. The price is the same.
- **A book that stopped quoting** is kept as an `unavailable` quote without outcomes in the as-of answer, where the
  provider simply no longer lists it. It counts toward nothing.
- **The flag also stops the prune and the index reclaim** (see "How to switch it on"): while it is off, stored rows
  outlive the 7- and 400-day retention, and an invalid index an interrupted rebuild left stays until it is on again.
- **Index rebuilds need the tables' owner.** The capture connects as the role whose migrations created the tables,
  so it may rebuild their indexes (on PostgreSQL 17, through the `MAINTAIN` privilege an owner has). A deployment
  that captured with a lesser role would record failed `reclaim` runs, and the files would grow to the ceiling.
- **The size an index needs is measured on synthetic data** (`INDEX_ROW_BYTES`, like `ROW_BYTES` for the cap). A
  real feed has other identifiers. Each rebuild of 10,000 rows or more records the size it really produced, and
  the check uses the larger of the two while that rebuild is among the last 50 reclaim runs (a reclaim run is
  written only when something was rebuilt, dropped or failed: 20 in the eight-day rolling measurement; once the
  rebuild has left that window the measured figure applies again until the next rebuild records a new one), so a
  feed with longer identifiers costs at most one rebuild of each index a day; measure both tables again when a
  real feed is connected.
- **Status records** older than the keep period are dropped one by one, each by its own age: a record that has not
  changed for 400 days is no longer among the entries, and the answer says from when records are kept
  (`kept_from`). If it was the event's only record, a read at a time after `kept_from` answers `not_captured`
  although a record stood then; `kept_from` is the only sign. P0.5 should store an unchanged record again from
  time to time (as the props capture does daily), or give that answer its own label.
- **The administrators' statistics** show the latest run of each kind with its counts, a failed run's error
  class, and the names and error classes of failed indexes. They show the latest run by id only: no history, no
  last successful capture when the latest one failed or was skipped, not whether an invalid index is on the disk
  now, no flag for "full" or "over the ceiling" (compare `disk_bytes` with `max_disk_bytes`), and the rows a
  cut-short prune deleted appear in no run's `rows_deleted`. On the preview these statistics and the worker's
  log are all an operator has; worth extending when someone operates this.
- **Not tried in the reference model:** a provider clock that steps back, two provider names in one archive,
  status records without an event, a keep period of 400 days with stays weeks apart (its three-stay scenarios
  use a keep period of nine days and stays two to four days apart; the production settings are in two
  hand-written tests), a game listed more than three times, and a capture that commits between two statements of
  a read (one hand-written test).
- **Status records** are stored only through `capture_status`, which nothing calls on a schedule until P0.5 supplies
  a lineup and news provider; P0.5's interface must produce `StatusRecord` or migrate the table.
- Line history, game logs and next events are not served from the archive (F17, F34).
- Partitioning, and leaving the archive out of backups, are not built.
- Web and mobile screens are not part of this item; F01, F03, F22 and F34 build on it.

## Flag and entitlement

- Flag `snapshot_archive`, default off everywhere. Off means the capture writes nothing and the user routes answer
  404 `feature_disabled`. The admin statistics route stays available.
- P0.1 is a foundation with no Tier, and P0.3 (entitlements) has not landed, so nothing is gated by plan. When P0.3
  lands, `archive.read` is to be enabled on every plan and each consumer item (F01, F03, F22, F34) gates its own
  surface with its own Tier. The existing, unused `odds_history_hours` entitlement is not applied to these routes;
  a limit on how far back a plan may query is a pricing decision (OQ-01).

## Hard rules

1. Nothing places, pre-fills or links to a wager; the responses carry no links.
2. Every archived row in a response carries its `captured_at`, and every user response carries `data_mode` and the
   time it answers for (`requested_as_of`, or `placed_at` for placement prices); the administrators' statistics
   carry run times only. No estimate is introduced.
3. Prices come only from stored quotes through `Board`; missing or uncertain inputs answer `cannot_price` with a
   named reason.
4. The archive is not an opportunity surface and sends nothing; consumer items call the P0.6 suppression hook.
5. Data comes only through the configured provider interface (synthetic here); nothing is scraped.
6. Nothing depends on state law.

Stop list: no item hit.

  - a counted cap of 1.5 GiB and a ceiling of 2 GiB on the files. Under default autovacuum expect the files near
    1.9 GiB with the counted size at the cap (measured: 1.215 to 1.24 times the largest counted size, 1.82 to

    capture pauses until the prune has made room; the synthetic schedule has 20;
  - a rebuild of the largest index at the cap needs about 0.5 GiB more disk and about 0.2 GiB of write-ahead log
    for some seconds, and a dump in progress can leave one extra index copy (256 MB at the cap) until it ends;
  - every restore keeps the replaced database in the server (up to about 1.9 GiB each at the cap), and no ops
    action removes it: decide whether to add one; dumps are about 60 MB each by day 400, about 1.15 GB across
