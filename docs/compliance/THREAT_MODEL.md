# OddVex — Threat model

Last updated: 2026-11-21 · Method: STRIDE per trust boundary · Status: **second pass, written from the code at
release `2b0c7c1` and from the state of the private preview on the Hostinger VPS on 2026-11-21. The first pass was
written at commit `bdd77a5` on 2026-11-16. Not reviewed by a security specialist. No penetration test has been
done.**

> Not a certification and not legal advice. This lists what the code does today, what it does not do, and who should
> pick up each gap. "Mitigation" means a control that exists in a cited file, not a control that has been attacked
> and held.

Scope: `services/api` (FastAPI), `apps/web` (Next.js), `apps/mobile` (Expo), the database, CI, and the private
preview deployed on the shared Hostinger VPS since 2026-11-18 (`infrastructure/hostinger/`): `preview.oddvex.com`
behind a password and `api-preview.oddvex.com` open to the internet. Threats that come from that server being
shared are in section 3.7.

Covered in this pass, and not in the first: feature flags, entitlements, the value screen, tracker analytics, admin
user management, email verification and password reset writing to an outbox, the community module (off by default),
the per-account limits, and the preview deployment.

Out of scope until they exist: licensed data provider, real sportsbook sync vendor, language-model assistant,
billing, push and real email delivery. Each needs its own pass before it ships.

## 2. Trust boundaries and data flow

```
 [Browser] ==B1== [shared Caddy] == [Next.js server] ==B2== [FastAPI] ==B3== [PostgreSQL]
 [Mobile app] ==B4== [shared Caddy] ===================== [FastAPI]
 [Operator] ==B5== [Hostinger Docker Manager -> ops container with the Docker socket] == [all OddVex containers, /opt/oddvex]
 [GitHub: contributors, Actions, dependencies] ==B6== [build artifacts, and ops.sh fetched by the ops container]
 [Other projects' containers on the shared proxy network] ==B7== [Next.js server, FastAPI]
```

| Boundary | Crossing | Authentication | Notes |
|---|---|---|---|
| B1 | Browser to Next.js, through Caddy | Caddy asks for the preview password on `preview.oddvex.com`. Then the `ov_session` cookie: `HttpOnly`, `SameSite=Lax`, `Secure` in production (`apps/web/src/lib/session.ts`) | The browser never sees the token (ADR-0003). Caddy holds only a hash of the preview password; the plain text is kept on the server in `/opt/oddvex/preview-password` (written by `ACTION=caddy` under `umask 077`, so mode 600 is expected; the file on the server was not inspected; `infrastructure/hostinger/ops.sh`) and is printed by that action (A-17, H-4) |
| B2 | Next.js server to API | Forwards the user's JWT as a bearer header, the visitor's address as `X-Forwarded-For` and a request id (`apps/web/src/lib/api.ts`, `apps/web/src/lib/request-meta.ts`, `apps/web/src/app/api/ov/[...path]/route.ts`) | **No service-to-service credential.** On the preview this is plain HTTP to `http://oddvex-api:8000` over the server's shared proxy network |
| B3 | API to database | Database password in `DATABASE_URL` | ORM only (`db/models.py`); no string-built SQL found. The database is only on the project's own network |
| B4 | Mobile to API | Bearer JWT from SecureStore (`apps/mobile/src/session/store.ts`) | Over the internet to `api-preview.oddvex.com`, which has no password. `EXPO_PUBLIC_API_URL` is public |
| B5 | Operators | Whoever can start a project in Hostinger's Docker Manager or holds a Hostinger API token with that access | Every operation is an `ops.sh` action; nobody has a shell on the server. The ops container mounts the Docker socket, `/opt/oddvex` and the shared Caddy directory |
| B6 | Contributors and dependencies | GitHub permissions | `.github/workflows/ci.yml`, `.github/dependabot.yml`, `.github/CODEOWNERS`. The ops container clones this public repository and runs `ops.sh` from `REF` (default `main`) |
| B7 | Neighbouring containers to OddVex | None | The proxy network `medivh-automation_default` is shared with the server's other projects. `oddvex-api` and `oddvex-web` are reachable on it by name without the preview password |

## 3. Threats, current mitigations and gaps

Risk is a coarse judgement for **launch with real users**: H, M or L. Owner names a role, not a person. To be
assigned: Founder. Rows changed in this pass say "Updated 2026-11-21".

### 3.1 Spoofing

| # | Threat | Boundary | Current mitigation (file) | Residual risk or gap | Risk | Proposed owner and next step |
|---|---|---|---|---|---|---|
| S-1 | Password guessing or credential stuffing | B2, B4 | Updated 2026-11-21. argon2id (`auth/security.py`), at most `ODDVEX_PASSWORD_HASH_CONCURRENCY` hashes at once (D-3). Per IP: 10 a minute across register, login, password change and the email routes (`ratelimit.py`, `auth/router.py`). Per account, over 15 minutes: 8 failed logins for one email from one network refuse that email from that network; 50 from all networks together refuse it everywhere (`check_login_allowed`, `config.py`). Failed logins audited (`auth.login_failed`); a dummy hash keeps timing the same for unknown emails | Guessing spread over many accounts from many addresses stays under every ceiling: about 50 guesses per account per 15 minutes. Containers on the shared network can forge addresses (S-6), which removes the per-IP and per-network limits for them; the per-email ceiling still holds. No breached-password check (AU-02). All counts are in process memory and reset when the API restarts, including at every deploy | M | Backend: shared counter store before more than one process; breached-password check. Founder: G-02 if the store is paid |
| S-2 | Stolen access token replayed | B1, B4 | Updated 2026-11-21. Token expires after `ODDVEX_JWT_TTL_MINUTES` (60). Logout (`POST /v1/auth/logout`, called by web and mobile), a password change and a suspension bump or check `token_version`/`status` and reject earlier tokens (`deps.py`, `auth/router.py`; D-009). Web cookie is `HttpOnly` | A copied token works until it expires or the owner logs out or changes the password. No refresh tokens, no per-session list, no device view; logout ends every session of the account (SECURITY_BASELINE AU-06 not met) | L | Backend: decide with the refresh-token design |
| S-3 | No second factor | B1, B4 | None | No MFA for users or admins. SECURITY_BASELINE AU-10 makes MFA mandatory for admins before production. The preview has no administrator yet | H for admins | Backend: MFA for admin accounts before the first administrator is made. Founder: confirm it blocks that (O-12) |
| S-4 | Admin role taken by someone who does not own the address | B5, B2 | Updated 2026-11-21. An account is an administrator exactly when its address is in `ODDVEX_ADMIN_EMAILS` **and** verified, in every environment (`deps.py`, `sync_admin_role`), checked at login, at email confirmation and on every token use. Promotion and demotion are audited (`role.granted`, `role.removed`); an address taken off the list loses the role at its next request. In production nothing can be verified through the API, so the first administrator is made by `scripts/bootstrap_admin.py`, run by `ACTION=admin`: it refuses an unlisted address, creates the account or takes over the existing one, sets a new random password, ends earlier tokens and email links, and audits `admin.bootstrap`. `ACTION=setenv` warns when the list holds the public contact address. A deploy refuses a commit without the script while the list holds an address. Tests: `tests/test_audit_auth_admin_role.py` | Having registered a listed address first gains nothing. What is left: whoever can run ops actions (B5) can make any listed address an administrator and read its password; the password is printed in the ops container's output (H-4); `ACTION=rollback` to a release from before the rule does not check the list; a deploy that loses the list demotes every administrator. No administrator exists on the preview (`ODDVEX_ADMIN_EMAILS` is empty) | M | Founder: name the first administrator (O-12). Operations: empty the list before rolling back to a release older than `2b0c7c1` |
| S-5 | Forged JWT | B2, B4 | HS256 with issuer check and required `exp`, `sub`, `iat`; algorithm pinned (`auth/security.py`). Production refuses to start with the development secret or one under 32 characters (`config.py`). The secret was generated on the server by the first deploy and is not in the repository | One symmetric secret, no key id, no overlap during rotation. No action rotates it on the preview (`infrastructure/RUNBOOK.md` section 7). The `role` claim is emitted but not trusted for authorization | M | Operations: a rotation action in `ops.sh` (G-09). Backend: key ids when rotation without sign-out is wanted |
| S-6 | Client forges its address to dodge limits or poison audit rows | B2, B4, B7 | Updated 2026-11-21. The API ignores `X-Forwarded-For` unless `ODDVEX_TRUST_PROXY=true`, then takes the last entry, printable text only, capped at 64 characters (`ratelimit.py`, `client_ip`). The web server sends exactly one address, the first hop it received, checked to contain IP characters only (`apps/web/src/lib/request-meta.ts`). On the preview the setting is `true` (`infrastructure/hostinger/compose.yaml`) and internet traffic reaches both containers only through the shared Caddy, which is expected to replace a client-supplied header (Caddy's default for a client that is not a trusted proxy; the live Caddyfile has not been inspected) | **The API trusts the header from any peer.** Every container on the shared proxy network (B7) can call `http://oddvex-api:8000` directly with a new `X-Forwarded-For` on each request: each value is a fresh per-IP bucket and a fresh per-network login count, so the 10-a-minute sign-in limit and the 8-per-network lockout never apply to it, and audit rows record the invented addresses. The per-email ceiling (50 in 15 minutes) and the per-user limits still apply. The same peers reach `http://oddvex-web:3000` without the preview password, and the web server passes the first hop of their header on. It needs a foothold in a neighbouring container (an automation workflow, or a request-forgery bug in another site on the server). **Options:** (a) honour the header only when the peer is the proxy, by its address on the shared network (Caddy, and the web container for web calls); (b) honour it only with a shared secret header that Caddy (`header_up`) and the web server add from the environment, compared in constant time, falling back to the peer address. Option (b) needs a migration path for the Caddy block already live (the `caddy` action only appends once) and puts the secret in a Caddyfile shared with other projects. **Deferred on 2026-11-21**; the decision log asks the Founder to choose or accept the risk (O-18) | M | Backend and operations: option (a) or (b) before a public launch on a shared server. Founder: O-18 |
| S-7 | Impersonating the web server to the API | B2 | Not needed: the API authorizes by user token only | No gap in authorization. Network allowlisting of the API is impossible while mobile calls it directly | L | None |
| S-8 | Phishing or lookalike domain | B1 | Updated 2026-11-21. The web app sends `Strict-Transport-Security: max-age=31536000; includeSubDomains` in production builds served over https (`apps/web/src/proxy.ts`, `apps/web/src/lib/csp.ts`); the API sends HSTS in production (`middleware.py`). The preview is `noindex, nofollow` (Caddy header) | No HSTS preload. Nothing in code stops a lookalike domain | L | Operations: consider preload at public launch |

### 3.5 Denial of service

| # | Threat | Current mitigation (file) | Residual risk or gap | Risk | Proposed owner and next step |
|---|---|---|---|---|---|
| D-1 | Flooding expensive endpoints | Updated 2026-11-21. Per-IP limits on sign-in and the assistant; per-user limits on bet and sync writes (120 a minute, 2,000 a day), exports (10 an hour) and streamed responses (8 at once); community limits; at most 5,000 bets per account; password-hash slots; body size limit (`ratelimit.py`, `config.py`) | **No limit on the public read routes** (events, odds, props, value screen, quant calculators) or on watchlist, alert and notification writes. Nothing limits requests in progress across accounts; the database pool is 15 connections and a request that waits 30 s answers 500. All in memory, per process. ## 6. Top risks before any real user

Ordered by judgement, not by score. Updated 2026-11-21.

1. **H-2 / T-7 / E-3**: control of the ops container, or of `main`, is root on a server shared with other projects;
   no Python lockfile, placeholder CODEOWNERS, branch protection unconfirmed.
2. **H-3 / I-5 / D-8**: every backup is an unencrypted full copy on the same disk, kept deleted accounts included; no
   off-server copy; restore never run on the server; no deletion ledger.
3. **S-3**: no MFA for admins, who can now act on every account and switch Founder-gated flags.
4. **D-1**: no limit on public read routes and no edge protection, on a shared 2-CPU server.
5. **S-6 / H-1**: neighbouring containers can reach the API and web directly and forge client addresses (deferred).
6. **H-5 / I-2**: the preview's API accepts sign-ups from anyone under draft legal pages and reveals registered
   addresses.
7. **D-2**: one account can be kept locked out through the per-email ceiling; recovery on the preview is clumsy.
8. **I-6 / I-7**: plain HTTP between containers on the shared network; nothing encrypted at rest.
9. **S-5**: no way to rotate the JWT secret on the preview.
10. No penetration test (SECURITY_BASELINE DS-09; needs spend, G-02).
11. Mobile app behaviour on a device not observed (M-1); preview APK signed with a public key (M-6).

Closed or reduced since the first pass: the shared web sign-in bucket (D-2), the allowlist admin path (S-4, E-2),
logout revocation (S-2), the missing CSP and HSTS on the web app (T-2, S-8), unaudited admin access and role changes
(R-1), the unscheduled alert evaluation (D-4), the in-memory export (D-5), query strings in logs (I-3).

## 7. Assumptions

- The API is reachable from the internet because the mobile app calls it directly. On the preview it is reached
  through the server's shared Caddy, which terminates TLS and is expected to replace a client-supplied
  `X-Forwarded-For` (not inspected).
- One API process. Its counters and limits reset when the container restarts.
- Hostinger operates the server and so holds what the preview stores. Whether it is a sub-processor needing G-13 is a
  question for counsel (decision log, gate table). No other third party receives user data.
